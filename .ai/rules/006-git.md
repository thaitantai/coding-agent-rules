# Git & Version Control Standards

## Context
- Applies to all git operations: commits, branches, PRs, and merges.
- Goal: a clean, readable history that serves as a second source of documentation.

## Branch Naming
```
<type>/<ticket-id>-<short-description>

feat/AUTH-42-google-oauth
fix/CORE-17-null-pointer-login
chore/DEV-5-upgrade-node-20
refactor/API-88-user-service-cleanup
```

Types: `feat`, `fix`, `chore`, `refactor`, `docs`, `test`, `hotfix`

## Commit Messages — Conventional Commits
Format: `<type>(<scope>): <imperative description>`

```
feat(auth): add Google OAuth login flow
fix(users): prevent null pointer on missing profile
refactor(api): extract validation middleware
test(orders): add integration tests for checkout flow
chore(deps): upgrade TypeScript to 5.4
docs(readme): update local setup instructions
```

Rules:
- Use imperative mood: "add feature" not "added feature" or "adds feature".
- Scope is optional but recommended: the module or area affected.
- Description under 72 characters.
- Body (optional): explain WHY, not WHAT. Reference ticket numbers.
- Breaking changes: add `!` after type: `feat(api)!: remove deprecated v1 endpoints`

## Commit Discipline
- One logical change per commit. Do not bundle unrelated changes.
- Never commit: secrets, `.env` files, `node_modules/`, `dist/`, build artifacts.
- Never commit code that breaks the build or fails tests (unless WIP branch).
- `git add -p` (patch mode) to stage only relevant hunks — avoid `git add .` blindly.
- Commit early, commit often on feature branches. Squash before merging.

## Pull Requests
- PR title follows the same Conventional Commits format.
- PR description must include:
  - **What**: brief summary of what changed.
  - **Why**: the reason/context (link to ticket/issue).
  - **How to test**: steps to verify the change works.
  - **Screenshots** (for UI changes).
- Keep PRs small and focused: target < 400 lines changed per PR.
- Split large features into sequential PRs if possible.
- Never merge your own PR without at least one review (except solo projects).

## Gitignore Essentials
Always ignore:
```
# Dependencies
node_modules/
.venv/
__pycache__/

# Build outputs
dist/
build/
.next/
out/

# Environment
.env
.env.local
.env.*.local

# OS & IDE
.DS_Store
Thumbs.db
.idea/
.vscode/settings.json  # (keep .vscode/extensions.json)

# Logs & cache
*.log
.turbo/
.cache/
coverage/
```

## Tags & Releases
- Use semantic versioning: `MAJOR.MINOR.PATCH` (e.g., `v2.3.1`).
- Tag releases on `main` / `master` only.
- MAJOR: breaking changes. MINOR: new features (backward compatible). PATCH: bug fixes.

## Rebase vs Merge
- Feature branches: rebase on `main` before merging (keeps history linear).
- Never rebase shared/public branches.
- Use `git merge --squash` or PR squash merge to keep `main` history clean.
